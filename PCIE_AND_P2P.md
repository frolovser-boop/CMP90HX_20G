## 1. Проблема ограничения шины PCIe на CMP 90HX

Штатно видеокарта CMP 90HX заблокирована в режиме **PCIe Gen1 x16**:
* Скорость передачи линии: 2.5 GT/s.
* Пропускная способность шины: ~3.2–3.5 ГБ/с в одну сторону.
* Поле `LnkCap2` в конфигурационном пространстве PCIe аппаратно зафиксировано на уровне `2.5GT/s only`.

### Влияние на инференс LLM:
* **Фаза Decode (генерация токенов):** Практически **не страдает**, так как веса модели уже загружены в локальную видеопамять, а передается только небольшой промпт и по одному токену на шаге (килобайты данных).
* **Фаза начальной загрузки (Model Load):** Загрузка 8–10 ГБ весов по PCIe Gen1 занимает ~3–4 секунды вместо ~1 секунды по Gen3.
* **Многокарточный инференс (Tensor Parallelism):** При разбиении одного слоя модели между несколькими GPU (например, в vLLM) карты должны обмениваться промежуточными тензорами (AllReduce) на каждом сгенерированном токене. На шине Gen1 со скоростью 3.5 ГБ/с это создает заметную задержку (latency bottleneck).

## 2. Разблокировка PCIe Gen2 x16 (~7 ГБ/с)

В проектах `cmp90hx_pwner` (rejoin16/17) и `jdowning100/cmpunlocker` был найден программно-аппаратный путь принудительного перевода шины в **PCIe Gen2**:

1. **Регистр LTSSM / XVE:**
   Через оверрайды регистров контроллера PCIe по адресу `0x00088fe8` и манипуляции с управляющим регистром `LINK_CONTROL` контроллер шины переводится в режим перекалибровки физического уровня (LTSSM link retraining).
2. **Результат перекалибровки:**
   * Скорость линка поднимается с 2.5 GT/s до **5.0 GT/s** (Gen2).
   * Реальная пропускная способность удваивается: **~6.8–7.2 ГБ/с** (полноценный Gen2 x16).
3. **Автоматизация через `cmp90hx_pwner`:**
   Пункт меню `2) PCIe GEN2` выполняет итеративный проход по всем обнаруженным картам, принудительно инициируя retrain до появления статуса `SUCCESS: GEN2 all/all`.

## 3. Включение CUDA P2P (Peer-to-Peer)

По умолчанию драйвер NVIDIA запрещает прямой доступ к памяти соседней карты (P2P direct memory access) для линеек CMP, принудительно направляя весь трафик через оперативную память хоста (Host RAM Bounce buffer).

### 3.1. Механизм разблокировки P2P
В скрипте `cmp90hx_pwner` разблокировка реализована через параметры загрузки патченного ядра `nvidia.ko`:
```bash
insmod /opt/cmp90hx/nvidia.ko \
    NVreg_EnableResizableBar=1 \
    NVreg_DmaRemapPeerMmio=0 \
    NVreg_RegistryDwords="PeerMappingOverride=1;ForceP2P=1;CLForceP2P=1"
```

### 3.2. Настройка подсистемы IOMMU в Linux
Для корректного сопоставления страниц памяти соседних карт без конфликтов контроллера виртуализации, IOMMU группы карт должны быть изолированы либо переведены в passthrough:
В `/etc/default/grub`:
```text
GRUB_CMDLINE_LINUX_DEFAULT="... intel_iommu=on iommu=pt pci=realloc,hpmemsize=8G,hpmmiosize=256M"
```
После обновления загрузчика (`update-grub`) и перезагрузки, статус P2P проверяется командой:
```bash
nvidia-smi topo -p2p r
nvidia-smi topo -p2p w
```
При успешной активации для всех пар карт CMP 90HX выводится матрица с флагом **`OK`**.

### 3.3. Скорость P2P в бенчмарках
* При включенном PCIe Gen2 реальная скорость копирования между двумя картами CMP 90HX составляет:
  ```text
  Bidirectional P2P Bandwidth: ~6.70 GB/s (буфер 256 MiB, 32 итерации)
  ```
* Этой пропускной способности достаточно для эффективной работы алгоритмов **Tensor Parallelism (TP=2)** в vLLM и llama.cpp.
