# Распайка шины PCI на CMP 90HX: анализ возможности разблокировки

> Вопрос: можно ли пайкой (распайкой) разблокировать шину PCIe до полноценной x16?
> Короткий ответ: **пайка — не тот инструмент для этой задачи**, и вот почему — с разбором
> по слоям ограничений и свежей разгадкой противоречия между двумя проектами.

---

## 1. Что именно ограничено (главный факт)

Из LnkCap карты (`BAR0 0x88084` = `0x00453d01`, сверено с конфиг-пространством):

| Поле LnkCap | Значение | Смысл |
|---|---|---|
| Max Link Speed [3:0] | `1` | 2.5 GT/s (**Gen1 — вот ограничение**) |
| Max Link Width [9:4] | `16` | **x16 — вся ширина заявлена карте** |

**⚠️ Поправка (2026-09-15, после статьи автора cmp90hx_pwner) + второе подтверждение
(issue #45 dartraiden/NVIDIA-patcher):** «заявлено» ≠ «физически разведено полностью».
**Стоковая CMP (подтверждено на 40HX и 90HX) тренируется всего x4**: на линиях 4–15
**отсутствуют разделительные конденсаторы**; LnkCap при этом анонсирует x16
(GPU-Z: `x16 1.1 @ x4 1.1` до пайки, `x16 1.1 @ x16 1.1` после). Лечение —
**допайка конденсаторов 220 нФ** на недостающие линии: автор pwner получил
физический x16 на всех 5 картах (tensor-split prefill +82%); arsevka — то же
на CMP 40HX независимо. Проверка своей карты: `stack/check.sh` печатает
фактическую ширину (`current_link_width`) — если видно x4 при LnkCap x16,
ищите пустые площадки конденсаторов вдоль линий. Детали:
[статья на Habr](https://habr.com/ru/articles/1082724/),
[issue #45](https://github.com/dartraiden/NVIDIA-patcher/issues/45).
Ограничение **скорости** (Gen1) при этом остаётся регистровым (см. ниже) —
конденсаторы его не снимают.

Блокировка стоит на **скорости** (Gen1 вместо Gen2/Gen3+), а это не вопрос меди,
это вопрос регистровой политики PHY-контроллера.

## 2. Иерархия замков: где именно стоит ограничение

(по `../cmp90hx-unlock/cmp90hx-unlock/docs/GEN3ADV_XP3G_RESEARCH.md`, кампания 2026-08-22,
и разбору `../cmp90hx_pwner/cmp90hxpwner.sh`)

| Слой | Что это | Пайкой управляемо? | Состояние |
|---|---|---|---|
| Страпы платы | Резисторы на PG132 | Да (перепайка) | **PCIe-страпов скорости нет** — на плате только RAMCFG (память). Скорость страпами на NVIDIA Ampere не задаётся |
| VBIOS init-таблицы | Прошиваемые | Флешер, не пайка | Не участвуют: анонс LnkCap идёт из железа, не из таблиц |
| LnkCap / LnkCap2 (анонс) | `0x88084` / `0x880a4` | Нет | **RO и для хоста, и для falcon** — запись отвергнута в тестах V2 (даже из контекста SEC2) |
| Link-policy регистры | `0x8C040`, `0x8C1C0`, `0x8C2C0`, `0x880A8` | Нет | Пишутся, но закрыты привилегированной маской XVE-домена |
| **Маска XVE `0x00088FE8`** | Привилегии PCIe-контроллера | Нет | 🔑 **Открывается V67-цепочкой (falcon)** — метод cmp90hx_pwner |
| PLM XP3G `0x8E1B0` | Другой привилегированный домен | Нет | Залочен и для хоста, и для falcon (кампания V5: readback `0xffffff8f`, rejected) |
| eFuse кристалла | Прожиг на фабрике | **Нет (это не пайка)** | «2.5GT/s-only» может быть фьюз-производным — но см. §4: на стенде pwner линк реально тренируется в Gen2 |

## 3. Что пайка могла бы теоретически — и почему не работает

1. **Переместить «страп скорости».** Такого страпа на плате нет. Все strap-группы
   PG132, известные из схемотехники (RAMCFG GROUP0/1/2), задают конфигурацию
   **памяти**, а не PCIe.
2. **Разогнать опорный Refclk (100 МГц → выше).** Скорость PCIe = refclk × PLL.
   Подача 150 МГц дала бы «3.75 GT/s»… до первого обмена: расхождение тактовой
   на 50% выходит за допуск CDR приёмника (±300 ppm) — линк не натренируется
   даже в Gen1. Плюс от refclk зависят PTIMER-детерминанты, нужные самой
   V67-цепочке. Тупик.
3. **Перепаять/удлинить линии данных.** Gen2 (5 GT/s) и тем более Gen3 (8 GT/s)
   требуют контролируемого импеданса и EQ; проводные перемычки убивают
   глазок — линк откатится на Gen1, т.е. результат обратный желаемому.
4. **Распаять больше линий.** Их уже 16 и они уже подключены.
5. **«Перепрошить фьюзы».** eFuse находятся внутри кристалла; физическая работа
   с ними — это не паяльная станция, а FIB-лаборатория. Экономически бессмысленно
   для карты за цену б/у RTX 3080.

**Вывод раздела: ни один реальный физический сценарий не даёт Gen2.**

## 4. Разгадка противоречия: почему pwner сообщает SUCCESS, а cmp90hx-unlock — «аппаратный потолок»

Два проекта целится в **разные регистры**:

| | cmp90hx-unlock (GEN3ADV) | cmp90hx_pwner (меню Gen2) |
|---|---|---|
| Цель-маска | XP3G PLM **`0x8E1B0`** | **`0x00088FE8`** (XVE-домен) + FEAT `0x00823800` |
| Путь открытия | Host → falcon (V67) — оба отклонены | V67-цепочка через falcon (как compute unlock) |
| Link-policy записи | Пытался писать `0x8C040/1C0` — rejected | **Не пишет вовсе** |
| После открытия | — | Только host-side: `setpci LnkCtl2 TLS=2` на EP и upstream + бит RL → retrain |
| Верификация | readback LnkCap | **Тройная**: sysfs `current_link_speed` = 5.0 GT/s + LnkSta EP = 5GT/s + LnkSta upstream = 5GT/s |
| Итог | «fuse-derived, software front closed» | «SUCCESS: GEN2 all/all» — линк реально натренирован |

Верификация pwner — настоящая (три независимых источника, включая состояние
upstream-порта), т.е. «успех» не является артефактом чтения. Механистическое
объяснение совместимо с обоими результатами: на GA102 запись **LnkCtl2 из
конфиг-пространства** (setpci) проходит мимо залоченного BAR0-зеркала `0x880a8`,
но PHY принимает целевую скорость только когда открыта **маска XVE `0x88FE8`**.
Кампания GEN3ADV эту маску не открывала — тестировала чужой (TU102-путь xrip)
адрес `0x8E1B0`. Поэтому вывод «fuse-derived» корректен лишь для XP3G-домена,
но, возможно, преждевременен для XVE-домена.

## 5. Порядок действий (decision tree) — до всякой пайки

```text
0. На своём железе: прочитать 0x00088FE8 (BAR0).
   ├── читается и = 0xffffffff  → XVE-маска открыта: прогоните retrain pwner'а,
   │                              проверьте Gen2 тройной проверкой. Пайка не нужна.
   └── читается 0xffffff8f (или stuck)
       1. Прогнать пункт "2) PCIe GEN2" cmp90hx_pwner (он сам откроет маску V67-цепочкой).
          ├── SUCCESS (тройная проверка) → Gen2 софтверно. Пайка не нужна. Финиш.
          └── FAIL на вашем экземпляре
              2. Взять ВТОРОЙ экземпляр 90HX (другая партия/ревизия) → повторить шаг 0–1.
                 (команда cmp90hx-unlock прямо рекомендует: «another 90HX sample»)
                 ├── Другой экземпляр открылся → лотерея ревизий; ваши карты — софтверно закрыты,
                 │   но аппаратно не «перепаиваемы» — см. §3.
                 └── Все экземпляры закрыты → остаётся только die-fuse work (FIB):
                     практически нецелесообразно. Проект считается закрытым по Gen2.
```

Практическое примечание: даже успех даёт **Gen2 x16 ≈ 7 ГБ/с** — это всё равно меньше
Gen3 x4 (8 GT/s × 4 = ~32 ГБ/с). Для инференса значение Gen2: вдвое быстрее загрузка
весов и вдвое меньше задержка TP-AllReduce. Decode-фазу Gen2 не ускоряет вообще
(узкое место — ПСП VRAM ~760 ГБ/с).

## 6. Если Gen2 недостижим — архитектурная компенсация (без пайки)

* **Pipeline Parallelism вместо Tensor Parallelism** для 2+ карт: TP делает
  AllReduce на каждом токене (болезненно на 3.5 ГБ/с), PP — только на границе
  слоёв (редкие передачи). На Gen1 x16 PP — правильная архитектура:
  `vllm --pipeline-parallel-size 2` либо `--tensor-parallel-size 1 --pipeline-parallel-size 2`;
  в llama.cpp — `--split-mode layer` с `--tensor-split`.
* **P2P даже на Gen1** полезен: прямой DMA убирает двойную копию через RAM
  и latency bounce-buffer'а.
* Веса — резидентно в VRAM: decode вообще не зависит от шины.

## 7. Итоговый вердикт

> **Скорость (Gen2): пайка не нужна и не поможет** — замок в маске XVE `0x88FE8`,
> путь программный и **теперь публично подтверждён** автором cmp90hx_pwner
> ([Habr, часть 3](https://habr.com/ru/articles/1082724/)): V67-открытие обеих
> масок + FLR + retrain → 5.0 GT/s x16, CUDA DMA 6.4 GB/s. Проверка других
> экземпляров не требуется — метод воспроизводим, автоматизация в его PWNER.
> **Ширина (x16): и здесь пайка возможна** — вопреки первоначальному выводу
> этого анализа, на части плат не хватает разделительных конденсаторов 220 нФ
> на старших линиях; допайка возвращает физический x16 (см. §1).
> См. `stack/check.sh` (печатает фактическую скорость и ширину линка) и
> `stack/p2p-setup.sh` (IOMMU + RegistryDwords для P2P).
