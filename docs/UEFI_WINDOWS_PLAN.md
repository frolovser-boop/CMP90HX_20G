# План: Windows-анлок CMP 90HX через UEFI (до загрузки ОС)

> Статус: ⬜ план (не реализовано). Оценка трудоёмкости: 1–3 недели работы с тестами.
> База: проверенный стек `cmp50hx-unlock` (efi-unlock + efi-unlock-windows) и `nv-uefi-unlocker`.

## 1. Почему UEFI-путь

* Патчи драйвера rejoin15 существуют только под Linux. Под Windows патчить модуль
  ядра NVIDIA практически невозможно (закрытый драйвер, подпись, PatchGuard).
* UEFI-анлок выполняется **до загрузки ОС**: цепочка V67 открывает PLM и пишет
  SS0/SS1, затем обычный Windows Boot Manager грузит систему со стоковым
  официальным драйвером. Никаких модификаций ядра.
* Ключевое условие сохранения состояния в ОС: `EnableGpuFirmware=1`
  (драйвер Windows должен работать через GSP, чтобы не перезатирать селекторы).
* **Прецедент есть с двух сторон:**
  1. `cmp50hx-unlock/efi-unlock/unlock50x_v1.c` прямо указывает, что его
     прародитель — unlock-код именно **CMP 90HX (GA102)** (через проект
     CMP40HX-Unlock и V67 «A Canary in the Crypto Mine»). Т.е. на GA102
     UEFI-цепочка уже когда-то работала.
  2. `nv-uefi-unlocker` v2.1.10 официально поддерживает всю линейку RTX 30
     (GA10x) — константы GA102 в его движке есть, но CMP 90HX (`10de:220d`)
     в allowlist не включён.

## 2. Две конкурирующие реализации — что выбрать

| | Маршрут 1: порт `unlock50x_v1.c` | Маршрут 2: allowlist в `nv-uefi-unlocker` |
|---|---|---|
| Кодовая база | gnu-efi, C, ~1 файл + FWSEC-блоб | Rust, зрелый релиз v2.1.10 |
| Расстояние до цели | Близко: предок — GA102-код; менять DeviceID, chipId0, FB-размер, FWSEC | Мало кода, но движок писался под retail-карты с VBIOS POST; поведение на карте без видеовыходов/PGRAPH не гарантировано |
| Windows-инсталлятор | Готовый (`efi-unlock-windows`: Go + BCD + BootOrder + BYOVD Gen2) | Свой (USB-загрузка, интерактивное меню) |
| Рекомендация | ✅ **Основной маршрут** | Запасной, если маршрут 1 упрётся в отладку |

## 3. Маршрут 1: конкретные изменения (checklist)

Файлы-источники: `../cmp50hx-unlock/efi-unlock/unlock50x_v1.c`, `extract_fwsec.py`,
`build.sh`; инсталлятор: `../cmp50hx-unlock/efi-unlock-windows/`.

1. **Цель устройства.** `10de:1e09` (50HX) → `10de:220d` (90HX).
   Subsystem может отличаться у вендоров (Manli/Colorful и др.) — матчить
   только по device ID.
2. **FALCON_RM / chipId0.** `0x162000A1` (TU102) → значение GA102
   (`0x172000A1`); сверить с BOOT_0 в дампе BAR0 на реальной карте или в
   исходниках `open-gpu-kernel-modules` (branch 610.43.03).
3. **fbSize в fake WPR meta.** 10 ГБ (0x280000000) — уже совпадает (90HX = 10 ГБ,
   6-й FBP отключён eFuse). Проверить, что fake WPR не заходит за 10 ГБ.
4. **FWSEC-блоб.** Извлечь нативный FWSEC из дампа PROM **CMP 90HX**
   (VBIOS PG132) скриптом `extract_fwsec.py` (адаптировать: имя дампа,
   геометрия V2 desc идентична). Нужен дамп вашей карты: `OMGVflash` или
   программатор SPI (см. `docs/20GB_PROCEDURE.md`, шаг 0).
5. **WPR2.** На 90HX WPR2-границы для 10 ГБ = значения 50HX
   (`027fee00:027fe000`), но сверить по живому dmesg Linux-стенда
   (`FWSEC_COMPLETE_GSP_UNTOUCHED`).
6. **Канареечный ROP (V67).** Плейлоад из 50HX-версии — без изменений
   (эксплойт семейства GA102 «приходит домой»); PLM-регистры те же
   (`0x00823804` → `0xffffffff`, SS0 `0x88888888`, SS1 `0x00000008`).
7. **SEC2 Booter.** 50HX грузит TU102-образ с патчем SIG_PROD@0x8700.
   Для 90HX нужен GA102-boter-образ — взять из дампа VBIOS 90HX
   (тот же путь extract, отдельная секция) или из GSP-пакета драйвера
   (`gsp_ga10x.bin` — booter внутри).
8. **Chainload-лестница.** Уже поддерживает `bootmgfw.efi` — оставить как есть.
9. **Windows-инсталлятор (Go).** Переименовать 50HX→90HX, заменить DeviceID
   в поиске PCI, заменить константы политик PCIe на GA102 (см. п. 10),
   embedded EFI пересобрать из нашего `unlock90x_v1.c`.
10. **Gen2 BYOVD.** Не обязателен (см. предостережение ниже); если делать —
    WinRing0/ThrottleStop-механизм переиспользуется, но TLS=5 GT/s надо
    писать в регистры GA102 (LTSSM/XVE `0x00088fe8`-семейство из
    `PCIE_AND_P2P.md`), а не TU102. **Учитывая аппаратный потолок
    `LnkCap2: 2.5GT/s only` (STATUS.md) — с вероятностью близкой к 100%
    retrain не пройдёт.** Оставить Gen2 как отдельный опциональный пункт,
    не блокирующий релиз.

## 4. Инфраструктурные требования (как у 50HX)

| Настройка UEFI | Значение |
|---|---|
| Above 4G Decoding | **Enabled** (буферы плейлоада >4 ГБ) |
| Secure Boot | Off (unsigned) / on с подписанным EFI (sign-efi.sh) |
| CSM | Disabled |
| Fast Boot | Disabled (иначе UEFI-шаг пропускается) |
| Resizable BAR | Auto/Enabled |

Windows: ключ `EnableGpuFirmware=1` в реестре драйвера
(`HKLM\SYSTEM\CurrentControlSet\Services\nvlddmkm\Parameters`,
DWORD `EnableGpuFirmware` = 1) — устанавливает инсталлятор 50HX-образца;
повторить это для 90HX-сборки.

## 5. План тестирования

1. **QEMU/OVMF smoke-тест** (обязательно, до железа): собранный EFI
   с фиктивным DeviceID → убедиться, что приложение не валит прошивку
   (грабли из истории: `OpenVolume` из загруженного приложения вешает
   целые семейства прошивок — в 50HX-коде SFS не используется вовсе).
2. **Железо, Linux-стенд** (двойная защита): поставить EFI рядом с GRUB,
   проверить, что после EFI-этапа Linux грузится и `stack/check.sh`
   показывает 9/9 FULL **со стоковым драйвером 610.43.03 без патчей**.
   Это главная точка истины.
3. **Windows**: стоковый WHQL-драйвер + `EnableGpuFirmware=1` →
   `nvidia-smi -q | grep -i "issue rate"`-аналог: прогон
   `stack/bench.sh` (GEMM FP16) на Windows-хосте; ориентир ~115 TFLOPS
   FP16 Tensor (Linux-ориентир).
4. **A/B**: снятие EFI-записи из BootOrder → убедиться, что карта
   возвращается в троттлинг (обратимость метода).
5. **Ночное отключение питания** → повторный вход в Windows → проверить,
   переживает ли анлок cold boot; если нет — оставить logon-таск из
   инсталлятора (по опыту RTX 3070/50HX так и делается).

## 6. Риски и откат

* Повешенная прошивка при сбое EFI-этапа — плата не грузится до
  сброса CMOS; риск снижается QEMU-прогоном и лестницей fallback
  (возврат BDS в BootOrder, как у 50HX).
* Эксплойт-цепочка не подписана никакой вендорской подписью —
  работает только при Secure Boot off или с собственным MOK/db.
* Полный откат: удалить UEFI boot entry (`50HX Unlock`), вернуть
  `bootx64.efi.90hx.bak`, выгрузить реестровые ключи инсталлятора.
* Карта остаётся «неотрицаемой»: eFuse не перепрограммируются —
  после удаления EFI состояние стока восстанавливается полностью.

## 7. Критерий готовности

> Windows-хост со стоковым WHQL-драйвером: `bench.sh` показывает
> FP16 ≥ 100 TFLOPS, GEMM FP32 ≥ 28 TFLOPS, pp512 12B Q4 ≥ 1600 t/s —
> и всё это переживает `shutdown -r` и (в идеале) полный cold boot.
